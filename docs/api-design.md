## 1. Conventions

| Topic | Rule |
|---|---|
| Base path | `/api/v1`. Breaking changes → `/api/v2`; additive changes allowed within v1. OpenAPI 3.1 generated by FastAPI, published per release. |
| Format | JSON (`application/json`), UTF-8, `snake_case` fields, timestamps RFC 3339 UTC, IDs UUID strings. OpenStack IDs are exposed as `openstack_id`. |
| Auth | Browser: server-side session cookie + CSRF token (UI). API: `Authorization: Bearer ovlm_<id>_<secret>` token, scoped (security-model.md §2.2). Unauthenticated: only `/healthz`, `/readyz`; `/metrics` is served on a separate internal port, not through the public listener (SEC-R-17). |
| Human-only endpoints | Approvals, typed destructive confirmations: accepted only from an interactive human session with re-auth within the last 5 minutes; tokens get `403` (security-model.md §7.2). This is the documented exception to FR-UI-3. |
| Scope | Every query is filtered by the caller's role-binding scope; out-of-scope resources return `404` (security-model.md §3.3). |
| Pagination | Cursor based: `?limit=` (max `api.max_page_size`, default TBD) and `?cursor=`; response `{"items": [...], "next_cursor": "..." | null}`. Cursor is opaque (encoded sort key + id). Stable order by `(created_at, id)` unless `sort` is one of the documented keys. |
| Filtering | Explicit query params per resource (e.g. `?status=gone&project=…`); no generic query language. |
| Errors | RFC 9457 `application/problem+json`: `type` (URI under `https://ovlm.dev/problems/<slug>` — placeholder domain), `title`, `status`, `detail`, `instance`, plus `code` (stable slug), `errors[]` for validation, `run_id`/`step_id` when relevant, and `next_action` (NFR-10: what state things are in, what to do next). Never secrets or raw stack traces. `detail` names only resources the caller may read; otherwise only the run id (SEC-R-31). |
| Async work | Anything that calls OpenStack, SSH or runs Ansible returns **`202 Accepted`** with `Location: /api/v1/runs/{id}` and the run body. Clients poll the run. A new run is in state `requested` until the worker admits it (locks, approval evidence, concurrency cap) or moves it to `rejected` with a reason (ADR-0003); a `requested` run shows the last worker heartbeat (SRE-R-25). Run actions are recorded as `run_signal`s; the worker re-validates actor, step-up and TC before acting; the run body lists pending signals (SRE-R-24). |
| Idempotency | `Idempotency-Key` header (client UUID) **required** on POSTs that start work (`/runs`, `/syncs`, `/assessments`, `/plans/{id}/start`, `/runs/{id}/actions/*`). Stored with (principal, method, path, body hash) for `api.idempotency_ttl`; replay returns the original response; same key + different body → `409 idempotency-key-reuse`. |
| Optimistic concurrency | Profiles, policies, services, plans return `ETag` (row `version`). `PUT`/`PATCH`/`DELETE` require `If-Match`; missing → `428`, stale → `412`. |
| Rate limits | Login and token endpoints per security-model.md §2.1; others unlimited in MVP. |

## 2. Roles

`viewer`, `operator`, `approver`, `admin` as defined in security-model.md §3.1 (admin does not inherit operator or
approver). "op" below = operator. SoD (requester ≠ approver; retirement two-person rule) is enforced server-side.

## 3. Resources

### 3.1 Clouds, projects, credentials (admin)

| Method + path | Role | Notes |
|---|---|---|
| `GET /clouds`, `GET /clouds/{id}` | viewer | |
| `POST /clouds`, `PATCH /clouds/{id}` | admin | |
| `GET/POST /projects`, `GET/PATCH /projects/{id}` | viewer / admin | project connection incl. `guest_access` |
| `POST /project-connections/{id}/credentials` `{kind, secret, app_credential_id?, expires_at?, stepup_id, typed_confirmation}` (as built; designed as `PUT /projects/{id}/credentials/{kind}`) | admin, human session + TOTP step-up + TC (connection name) | write-only secret; api seals it (security-model.md §5.1); response shows metadata only. **Rotation** (SEC-R-13): the cloud admin creates the new application credential out of band; the OVLM admin uploads it with its `expires_at`; a `credential_test` run validates it (project id, role list); on success the worker switches atomically and marks the old one `superseded` with `cloud_deletion_pending` and a reminder. OVLM never creates or deletes application credentials (a restricted one cannot, OSI §8 SV) |
| `POST /credentials/{id}/validate` (as built; designed as `POST /projects/{id}/credentials/{kind}/test`) | admin | **202** run (`credential_test`, worker): token issuance plus GET-only probes through the `ReadClient` hook for **both** credential kinds; records in `validation_result` whether the token's project id equals the project record and the role list is the expected one; no token or catalog stored (SEC-R-32) |
| `DELETE /credentials/{id}` (as built) | admin + step-up + TC | refused `409` while a run uses it |

### 3.2 Inventory (observed)

| Method + path | Role | Notes |
|---|---|---|
| `POST /projects/{id}/syncs` | op or admin (token scope `inventory:sync` or `operate`) | `{id}` is the project connection id. **202** run (`inventory_sync`); **409** `sync-already-pending` while a sync of that project is queued or running (the run id is in `detail`); 404 when the project is not visible; 409 `project-disabled`. The worker uses the connection's validated read credential and refuses a token scoped to another OpenStack project. The worker also queues one per eligible connection every `inventory.sync_interval` (0: off) |
| `GET /projects/{id}/syncs`, `GET /syncs/{id}` | viewer | `items`: sync records (status, kind, counts, `error` = `{"code": ...}`, `workflow_run_id`); `runs`: the recent sync runs (state, origin `api`/`periodic`, `end_reason`: why one ended, as a fixed code such as `credential_unavailable`, `auth_failed`, `project_mismatch`, `cloud_error`; never exception text, security-model.md §4.1) |
| `GET /servers?project=&status=&tag=&registered=` | viewer | observed servers |
| `GET /servers/{id}` | viewer | observed fields + attachments + ports + FIPs + revisions link |
| `GET /servers/{id}/revisions` | viewer | snapshot history |
| `GET /volumes`, `/ports`, `/floating-ips`, `/images`, `/flavors` (+ `/{id}`) | viewer | |
| `GET /orphans` | viewer | `ovlm:*`-marked resources not in the ledger or of terminal runs, excluding anything a current service, managed VM or profile references (ADR-0005). **Report-only** in MVP: evidence and a suggested CLI command; there is no delete endpoint (SEC-R-25) |

### 3.3 Services, managed VMs, profiles

| Method + path | Role | Notes |
|---|---|---|
| `GET/POST /services`, `GET/PATCH/DELETE /services/{id}` | viewer / op | DELETE only if no managed VM is `current` |
| `POST /services/{id}/managed-vms` `{observed_server_id}` | op | registration: **201** with the managed VM (created synchronously) and `host_key_scan_run`, the `host_key_scan` run it queued (worker: `ssh-keyscan` of `fixed_ips[0]` of the service floating IP's port, the address the renewal uses, security-model.md §6.2.1; the preferred key's fingerprint goes to `ssh_host_key_fingerprint`) |
| `POST /managed-vms/{id}/host-key-scans` | op | **202** run (`host_key_scan`); a queued scan is returned (`already_pending`). A scan never replaces a **confirmed** fingerprint: a different key fails the run ("host key changed") |
| `POST /managed-vms/{id}/host-key/confirm` `{fingerprint}` | op, human session (matrix `host_key.confirm`) | the operator confirms the scanned fingerprint after comparing it out of band (the VM's console or `ssh-keygen -lf` on the VM). The body must equal the scanned value: 409 `host-key-not-scanned`, 409 `host-key-mismatch`, 422 malformed; idempotent; audited (ADR-0006). `POST /plans` is refused (409 `host-key-unconfirmed`) until the current VM's key is confirmed: the renewal reaches blue only with this fingerprint |
| `GET /managed-vms`, `GET /managed-vms/{id}` | viewer | response has `desired` (profile version) and `observed` blocks separately (FR-REG-4), plus `drift` (V1) |
| `DELETE /managed-vms/{id}` | op | unregister; refused while a run holds the service lock |
| `GET/POST /services/{id}/profiles`, `GET /profiles/{id}` | viewer / op | |
| `POST /profiles/{id}/versions` (`If-Match`) | op | creates an immutable version. **Not in this release:** it starts no worker `automation_lint` run (no such job exists yet), so a version shows `lint_status: pending` and `lint_result: null`. Validation errors as problem+json `errors[]` (unpinned SHA, branch ref, non-allowlisted repo, >1 data volume, `secret_ref` of another service (SEC-R-27) …). A plan on a version whose lint failed is refused unless a waiver exists |
| `POST /profiles/{id}/versions/{n}/lint-waivers` `{rule, path_glob, reason, stepup_id}` | approver, human session + TOTP step-up (`lint_waiver.grant`, target: the version id) | 201, audited `lint_waiver` row; one rule (`no_log_secret`, `check_mode_forced`, `delegate_to`, `ignore_errors`; the data-safety rules are never waivable), a repository-relative glob that keeps one literal path segment (`*`, `**/*`, `[a-z]*` refused, SFR-2), a reason of 10 to 1000 characters; refused (403 `sod-violation`) if the caller is the version author or in the requester set of any plan on that version, whatever `allow_operator_approver` says; a password-only step-up answers 403 `totp-required`. The active waivers are bound into the plan hash and listed in every later approval's `hash_inputs` (SEC-R-36) |
| `GET /profiles/{id}/versions/{n}/lint-waivers[?include_revoked=true]` | viewer | the version's active (or all) waivers |
| `POST /lint-waivers/{id}/revoke` `{reason, stepup_id}` | approver, human session + TOTP step-up (`lint_waiver.revoke`, target: the waiver id) | the waiver stays as a row, `state: revoked`; 409 if already revoked; audited |
| `GET /profiles/{id}/versions`, `/versions/{n}` | viewer | |

### 3.6 Planning and approvals

| Method + path | Role | Notes |
|---|---|---|
| `GET /renewals/upcoming?before=` | viewer | FR-PLN-1 |
| `POST /plans` `{managed_vm_id, planned_window_start}` | op | resolves image (unique match, owner, visibility, hash fields), flavor, SG **IDs**, other IDs, capacity (advisory), conflicts; copies `auto_restore_in_window` and `max_window_duration` from the policy version; computes `plan_hash`; starts a worker `automation_diff` run; `201` (no OpenStack call in api: uses latest inventory; the run re-validates live) |
| `GET /plans/{id}`, `GET /plans` | viewer | |
| `POST /plans/{id}/approval-requests` | op | creates `approval` request (subject `plan`); `409 diff-pending` until the automation diff is available |
| `GET /approvals/{id}` | viewer | `self_approved` flag, decider `account_provenance` (G3), `hash_inputs` (profile version, SHA, repo URL, target names + ids, data volume id, SG ids, image id + owner, policy version incl. `auto_restore_in_window` and `max_window_duration`), `requester_set` (names), `automation_diff` (or "first approval of this repo"), `sod_allowance` if any, `blast_radius` (§4) |
| `POST /approvals/{id}/decision` `{decision, typed_confirmation?, comment}` | approver, **human session + TOTP step-up** (single-use, bound to this approval) | `typed_confirmation` required for cutover and retirement gates: `<server name> <last 6 chars of server id>` checked server-side; decision bound to current `bound_hash`; `409 approval-voided` if hash changed; `403 sod-violation` if the caller is in the requester set (profile version author, plan creator, run starter, policy editor, requester) or holds `operator` in the same scope, unless the installation allows it, in which case the approval is recorded `self_approved` (never for retirement) (SEC-R-2, M9) |
| `GET /approvals?state=open` | viewer | |
| `POST /plans/{id}/start` | op (requester may start; approval by someone else) | **202** run in `requested`; refuses early if approval missing/expired/voided, locks visibly unavailable (`409 resource-locked`, advisory pre-check), concurrency cap reached (`409 capacity`), readiness not `ready`. The worker's admission is authoritative (run → `rejected` with reason) |

### 3.7 Runs (workflow)

| Method + path | Role | Notes |
|---|---|---|
| `GET /runs?kind=&state=&service=` | viewer | |
| `GET /runs/{id}` | viewer | state, phase, current step, downtime timestamps, locks held, `current_truth` + `current_truth_at`, `available_actions[]` (each with role needed and concrete effect from the current state), worst-case window and budget, links |
| `GET /runs/{id}/steps`, `GET /steps/{id}`, `GET /steps/{id}/attempts` | viewer: status, evidence summary, Ansible `result` and per-task changed/ok/failed; **operator/admin**: automation logs, events and diffs (restricted artefacts, "reported by guest" labels, SEC-R-3, SEC-R-31). Running steps show `lease_owner`, `lease_expires_at`, `heartbeat_at`, worker `last_seen_at` | |
| `POST /runs/{id}/actions/probe` | op | read-only re-probe (read credential + read-only SSH); refreshes `current_truth`; no TC (SRE-R-9) |
| `POST /runs/{id}/cutover-request` | op | creates the G2 approval request (renewal-workflow.md §3) |
| `POST /runs/{id}/retirement-request` | op | creates the G3 request; allowed only after retention elapsed |
| `POST /runs/{id}/actions/retry-step` | op | only in `needs_human`/`failed`; new attempt starts with probe |
| `POST /runs/{id}/actions/abort` `{typed_confirmation}` | op, human session + TC | sets `abort_requested`; effect depends on phase (renewal-workflow.md §5) |
| `POST /runs/{id}/actions/rollback` `{typed_confirmation}` | op, human session + TC | build phase: delete green; window: run restore sequence |
| `POST /runs/{id}/actions/revert` `{typed_confirmation}` | op, human session + TC | after cutover until retirement: restore sequence (FIP back to blue) |
| `POST /runs/{id}/actions/reprepare-automation` `{typed_confirmation, stepup_id}` | **approver** (not the run's requester: 403 `sod-violation`), human session + step-up + TC | only on a step parked on a lost/unverifiable automation checkout (else 409 `not-applicable`); authorizes one re-clone of the pinned SHA inside the window (renewal-workflow.md §2, AC §2) |
| `POST /runs/{id}/actions/mark-resolved` `{step_id, attestation, typed_confirmation}` | op + TC; approver if next step is destructive (security-model.md §3.1) | operator states the manual fix (e.g. admin force-detached); engine re-probes before continuing |

All action POSTs require `Idempotency-Key`, return **202** with the run, and are audited. A 403 for a missing role names the account: `Signed in as approver-a (approver). This action needs the operator role.` Every web page header shows `username · role (scope)` for each effective binding and a "Sign out / switch account" button (UI-1).

### 3.8 Audit, system

| Method + path | Role | Notes |
|---|---|---|
| `GET /audit?actor=&target=&run=&from=&to=&limit=&cursor=` | viewer (scoped); tokens with `read` | Newest first; `{items, next_cursor}`, `limit` 1-200 (default 50), opaque `cursor` (`400 invalid-cursor` if malformed). `actor` is a user id, `target` a target id, `from` inclusive and `to` exclusive (UTC if no offset). **Scope**: only events of projects the caller may view; an event of another project is absent, never a 403 or a count. Events the worker records without a project (they carry a run id) follow the run's plan project; events with neither are for global bindings only. **Per-role action allowlist** (SEC-R-31): `auth.*`, `authz.*`, `token.*`, `user.*` and `role_binding.*` events are returned only to a human admin with a global binding, whatever the filters. **`run=`** returns one run's whole trail: events of the run id, of its steps (`step_id`, or a step as target), of the run as a target, of the run's plan, and of **every approval of that plan** (G1 belongs to the plan, not the run; G2 and G3 too). The engine's own events are in the table too: `step.claim` (or `step.takeover`) and `step.outcome` (one row per claim and one per outcome, so a waiting step has one pair per poll attempt; never per heartbeat), `step.parked`, `run.admitted`, `run.needs_human`, `run.<final state>` and `signal.<kind>`, with `principal_type` `worker` (a signal carries its sender), `after` limited to allowlisted fields (step key, attempt, state, error class; never the fencing token) and the engine's own result in `after.engine_result`. Each event carries every recorded column as recorded (`before`/`after` were allowlisted when written, so no secrets) |
| `GET /audit/export` (V1, JSON lines) | admin | |
| `GET /healthz`, `GET /readyz` | none | architecture.md §6; `/metrics` on the internal port only |
| `/users`, `/role-bindings`, `/tokens`, `/session` | per security-model.md | `POST /users` and password reset return a **one-time enrolment link**; the admin never sets or sees a password; first login forces a password change and, for `approver`/`admin`, TOTP enrolment in the user's own session (SEC-R-11) |
| `POST /session/totp/enrol`, `POST /session/totp/confirm` | the user, own session | TOTP mandatory for `approver` and `admin` in MVP (M9, SEC-R-10) |
| `POST /session/reauth` `{password, totp_code, action, target_id}` | the user | returns a single-use `stepup_id` valid ≤ 5 min for exactly that action and target; approvals and TCs must present it (SEC-R-10) |
| `GET/PUT /settings/auth` `{allow_operator_approver}` | admin, human session + TOTP step-up + TC | installation setting (default false, M9); history kept, audited |

## 4. Destructive endpoints and confirmation

| Action | Endpoint | Confirmation |
|---|---|---|
| Enter downtime window (stop blue, detach, attach, FIP move) | `POST /approvals/{id}/decision` for the cutover gate (or, when policy needs no cutover approval, `POST /runs/{id}/cutover-request` with `typed_confirmation` by the operator in a human session) | TC of **blue** `name + last 6 ID chars`; approval bound to plan hash |
| Revert after cutover | `POST /runs/{id}/actions/revert` | TC of blue |
| Rollback / abort | `POST /runs/{id}/actions/rollback`, `/abort` | TC of the affected VM (green in build phase, blue in window) |
| Retire (delete blue) | approval decision on the retirement gate (two-person rule) | TC of blue |
| Credential delete/replace | `DELETE/PUT /projects/{id}/credentials/{kind}` | admin + TC |

Request field: `"typed_confirmation": "app01-prod 3f9c2a"`. The server compares against current DB values (not the
client's copy); mismatch → `422 confirmation-mismatch`. The response of every pre-confirmation `GET` (run, approval)
includes a `blast_radius` object: service, VMs (name, id), volume, FIP, expected outage start, gate validity (FR-UI-2);
for the cutover gate also the worst-case window (Σ step deadlines W1–W10 + S1–S10), the `max_window_duration` budget,
whether a pre-handoff snapshot is taken ("no: revert carries green's writes forward") and the automatic-restore
statement, including the D-1 rule for failures after the service starts on green: "stops and pages an operator" (no
snapshot) or "restored automatically, snapshot kept" (renewal-workflow.md §3, §4.1); for the retirement gate the X1 probe evidence (green health age, volume
attachment, FIP port). No endpoint accepts a `force` flag. There is no orphan delete endpoint (SEC-R-25).

## 5. Example: start a renewal

```
POST /api/v1/plans/7c1e…/start
Idempotency-Key: 0b8d6f52-…
→ 202 Accepted
Location: /api/v1/runs/01934c…
{"id":"01934c…","kind":"renewal","state":"requested","phase":"build",
 "current_step":null,"links":{"steps":"/api/v1/runs/01934c…/steps"}}
```

```
409 application/problem+json
{"type":"https://ovlm.dev/problems/resource-locked","title":"Resource is locked by another run","status":409,
 "code":"resource-locked","detail":"Volume 5d2a… is held by run 0193a1… (state: retained).",
 "next_action":"Wait for run 0193a1… to retire or revert, or abort it."}
```
