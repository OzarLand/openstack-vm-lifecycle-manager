Authentication, roles, step-up re-auth, token scopes and CSRF are defined in [security-model.md](security-model.md)
(§2, §3, §7); this document applies them. The UI (ADR-0002) calls the same service functions as these endpoints.

## 1. Conventions

| Topic | Rule |
|---|---|
| Base path | `/api/v1`. Breaking changes → `/api/v2`; additive changes allowed within v1. OpenAPI 3.1 generated by FastAPI, published per release. |
| Format | JSON (`application/json`), UTF-8, `snake_case` fields, timestamps RFC 3339 UTC, IDs UUID strings. OpenStack IDs are exposed as `openstack_id`. |
| Auth | Browser: server-side session cookie + CSRF token (UI). API: `Authorization: Bearer ovlm_<id>_<secret>` token, scoped (security-model.md §2.2). Unauthenticated: only `/healthz`, `/readyz`, `/metrics` (metrics may be restricted by the proxy). |
| Human-only endpoints | Approvals, typed destructive confirmations: accepted only from an interactive human session with re-auth within the last 5 minutes; tokens get `403` (security-model.md §7.2). This is the documented exception to FR-UI-3. |
| Scope | Every query is filtered by the caller's role-binding scope; out-of-scope resources return `404` (security-model.md §3.3). |
| Pagination | Cursor based: `?limit=` (max `api.max_page_size`, default TBD) and `?cursor=`; response `{"items": [...], "next_cursor": "..." | null}`. Cursor is opaque (encoded sort key + id). Stable order by `(created_at, id)` unless `sort` is one of the documented keys. |
| Filtering | Explicit query params per resource (e.g. `?status=gone&project=…`); no generic query language. |
| Errors | RFC 9457 `application/problem+json`: `type` (URI under `https://ovlm.dev/problems/<slug>` — placeholder domain), `title`, `status`, `detail`, `instance`, plus `code` (stable slug), `errors[]` for validation, `run_id`/`step_id` when relevant, and `next_action` (NFR-10: what state things are in, what to do next). Never secrets or raw stack traces. |
| Async work | Anything that calls OpenStack, SSH or runs Ansible returns **`202 Accepted`** with `Location: /api/v1/runs/{id}` and the run body. Clients poll the run. |
| Idempotency | `Idempotency-Key` header (client UUID) **required** on POSTs that start work (`/runs`, `/syncs`, `/assessments`, `/plans/{id}/start`, `/runs/{id}/actions/*`). Stored with (principal, method, path, body hash) for `api.idempotency_ttl`; replay returns the original response; same key + different body → `409 idempotency-key-reuse`. |
| Optimistic concurrency | Profiles, policies, services, plans return `ETag` (row `version`). `PUT`/`PATCH`/`DELETE` require `If-Match`; missing → `428`, stale → `412`. |
| Rate limits | Login and token endpoints per security-model.md §2.1; others unlimited in MVP. |

## 2. Roles

`viewer`, `operator`, `approver`, `admin` as defined in security-model.md §3.1 (admin does not inherit operator or
approver). "op" below = operator. SoD (requester ≠ approver; retirement two-person rule) is enforced server-side.

## 3. Resources

### 3.6 Planning and approvals

| Method + path | Role | Notes |
|---|---|---|
| `GET /renewals/upcoming?before=` | viewer | FR-PLN-1 |
| `POST /plans` `{managed_vm_id, planned_window_start}` | op | resolves image/flavor/IDs, capacity (advisory), conflicts; computes `plan_hash`; `201` (no OpenStack call in api: uses latest inventory; the run re-validates live) |
| `GET /plans/{id}`, `GET /plans` | viewer | |
| `POST /plans/{id}/approval-requests` | op | creates `approval` request (subject `plan`) |
| `POST /approvals/{id}/decision` `{decision, typed_confirmation?, comment}` | approver, **human session + step-up** | `typed_confirmation` required for cutover and retirement gates: `<server name> <last 6 chars of server id>` checked server-side; decision bound to current `bound_hash`; `409 approval-voided` if hash changed |
| `GET /approvals?state=open` | viewer | |
| `POST /plans/{id}/start` | op (requester may start; approval by someone else) | **202** run; refuses if approval missing/expired/voided, locks unavailable (`409 resource-locked`), concurrency cap reached (`409 capacity`), readiness not `ready` |

### 3.7 Runs (workflow)

| Method + path | Role | Notes |
|---|---|---|
| `GET /runs?kind=&state=&service=` | viewer | |
| `GET /runs/{id}` | viewer | state, phase, current step, downtime timestamps, locks held, links |
| `GET /runs/{id}/steps`, `GET /steps/{id}`, `GET /steps/{id}/attempts` | viewer | evidence; automation logs (redacted, "reported by guest" labels) |
| `POST /runs/{id}/cutover-request` | op | creates the G2 approval request (renewal-workflow.md §3) |
| `POST /runs/{id}/retirement-request` | op | creates the G3 request; allowed only after retention elapsed |
| `POST /runs/{id}/actions/retry-step` | op | only in `needs_human`/`failed`; new attempt starts with probe |
| `POST /runs/{id}/actions/abort` `{typed_confirmation}` | op, human session + TC | sets `abort_requested`; effect depends on phase (renewal-workflow.md §5) |
| `POST /runs/{id}/actions/rollback` `{typed_confirmation}` | op, human session + TC | build phase: delete green; window: run restore sequence |
| `POST /runs/{id}/actions/revert` `{typed_confirmation}` | op, human session + TC | after cutover until retirement: restore sequence (FIP back to blue) |
| `POST /runs/{id}/actions/mark-resolved` `{step_id, attestation, typed_confirmation}` | op + TC; approver if next step is destructive (security-model.md §3.1) | operator states the manual fix (e.g. admin force-detached); engine re-probes before continuing |

All action POSTs require `Idempotency-Key`, return **202** with the run, and are audited.

## 4. Destructive endpoints and confirmation

| Action | Endpoint | Confirmation |
|---|---|---|
| Enter downtime window (stop blue, detach, attach, FIP move) | `POST /approvals/{id}/decision` for the cutover gate (or, when policy needs no cutover approval, `POST /runs/{id}/cutover-request` with `typed_confirmation` by the operator in a human session) | TC of **blue** `name + last 6 ID chars`; approval bound to plan hash |
| Revert after cutover | `POST /runs/{id}/actions/revert` | TC of blue |
| Rollback / abort | `POST /runs/{id}/actions/rollback`, `/abort` | TC of the affected VM (green in build phase, blue in window) |
| Retire (delete blue) | approval decision on the retirement gate (two-person rule) | TC of blue |
| Delete orphan | `DELETE /orphans/{id}` | admin/approver per security-model.md §7.1 + TC |
| Credential delete/replace | `DELETE/PUT /projects/{id}/credentials/{kind}` | admin + TC |

Request field: `"typed_confirmation": "app01-prod 3f9c2a"`. The server compares against current DB values (not the
client's copy); mismatch → `422 confirmation-mismatch`. The response of every pre-confirmation `GET` (run, approval)
includes a `blast_radius` object: service, VMs (name, id), volume, FIP, expected outage start, gate validity (FR-UI-2).
No endpoint accepts a `force` flag.

## 5. Example: start a renewal

```
POST /api/v1/plans/7c1e…/start
Idempotency-Key: 0b8d6f52-…
→ 202 Accepted
Location: /api/v1/runs/01934c…
{"id":"01934c…","kind":"renewal","state":"running","phase":"build",
 "current_step":{"step_key":"preflight","state":"ready"},"links":{"steps":"/api/v1/runs/01934c…/steps"}}
```

Error example:

```
409 application/problem+json
{"type":"https://ovlm.dev/problems/resource-locked","title":"Resource is locked by another run","status":409,
 "code":"resource-locked","detail":"Volume 5d2a… is held by run 0193a1… (state: retained).",
 "next_action":"Wait for run 0193a1… to retire or revert, or abort it."}
```
