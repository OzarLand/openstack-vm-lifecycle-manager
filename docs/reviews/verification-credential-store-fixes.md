## Verdict

**CS-1 and CS-2 are closed.** The AEAD associated data now binds the credential row, the project connection, the
kind, the cloud and a digest of the endpoint (`auth_url`, region, interface, CA bundle hash). The worker rebuilds
that binding from the **live** connection and cloud rows, refuses on a mismatch before it decrypts anything, and
then sends the secret only to the endpoint it just authenticated. That last step uses the same row snapshot
(`ConnectionInfo`), so nothing can change in between. So the database role can rewrite any endpoint row and the
worst outcome is denial of service, never disclosure. The tombstones and the binding triggers resisted every bypass
I tried as `ovlm_api`.

CS-3, CS-4, CS-5, CS-7, CS-8 and CS-9 are closed. CS-10 is closed in substance: the api refuses to seal to a key
the worker did not announce. The `/readyz` signal is not done, and the docs say so. As the author said, CS-6 is
still open. I found three new Low findings and one Info. None of them blocks a merge.

**Fit to merge: yes.** Before a real credential is uploaded, run the CS-3 lab check that Keystone's default policy
lets the owner read its own application credential record. CS-6 should land before production.

## New findings

| ID | Severity | Where | Finding | Suggested action |
|---|---|---|---|---|
| N-1 | Low | `connections_0002.py:146-149` (`ovlm_api` keeps `UPDATE (guest_access)`), `api.py:255-273` | Only the API route protects `guest_access` (the jump host the guest key would be used through), with a step-up. The `ovlm_api` role can still rewrite it directly, and it is not in the `ssh_key` binding. The impact today is nil: no renewal code reads the connection's `jump_host` yet (`grep jump_host src/ovlm` matches only `connections/`), and SSH public-key authentication sends a signature, never the private key. | When the jump host is wired into the runner, add a digest of `guest_access` to the `ssh_key` binding, or pin the jump host's host key outside what `ovlm_api` can write. Until then, the docs could say the step-up is an API-level control only. |
| N-2 | Low | `validation.py:240` | The "unrestricted" check fails open when Keystone omits both the token's `restricted` flag and the record's `unrestricted` field (both `None`). The review asked to refuse unrestricted credentials. Current Keystone releases always return `unrestricted` in the record, so this is hardening. | Refuse when `record_unrestricted is None` and the record was read. Add it to the CS-3 lab check. |
| N-3 | Low | `store.py:97-120`, `store.py:137-148`, `keyring.py:96-99` | Rejected `ovlm-env-v1` credentials still reference their sealed secret. After a KEK rotation, the re-wrap counts them as `unknown_key` on every run and `kek_usage` keeps the old key "in use", so `ovlm kek status` stays at exit 3 and the old key can never be retired by the documented procedure. The author says no v1 credential exists in practice, so this is operational only. | Delete rejected v1 credentials in the migration (or in a worker sweep, audited), or exclude `alg = 'ovlm-env-v1'` from usage and re-wrap. |
| N-4 | Info | `docs/credential-store.md` §7 | The docs say a redirect "invalidates its credentials … visible in `credential.validate` audit rows". When the `ovlm_api` role writes the cloud row directly, no re-validation is requested. The credential shows `ok` until the next periodic run (up to 24 h), but every use in the meantime is refused by `usable_row`. Fail closed; only the signal is late. | Optional: a statement trigger on `cloud` endpoint columns that bumps `validation_requested_at`. Or say in the docs that detection may take up to the re-validation interval. |
