## Verdict

**Accept with required changes.** The security model is coherent, honest about residual risk, and its OpenStack permission claims match openstack-integration.md in every case I checked (§1.1, §1.2, T3, §4.1, §4.2 both tables, §4.3, §4.4, §6.1, §7.1). The controls that matter most (two credentials, worker-only write path, ownership guard with DB-and-tag, approval hash binding, append-only audit at the GRANT level, pinned automation SHA, untrusted guest output) are the right ones. The gaps are mostly places where a stated guarantee is stronger than what the design delivers, or where a control is stated but its inputs are not observable with the credential OVLM holds.

| SEC-R-1 | High | security-model §1.2, §1.3 T7, §5.1 "Process separation", §8, §9 | The model claims "api compromise must not be [worker compromise]" and defends only the *credential* (api cannot decrypt). But api holds the runtime DB role and the worker trusts DB rows: a compromised api can insert a forged approval, a forged typed confirmation, a forged step-up record, or a plan whose target is any VM in the project, and the worker will execute it with the write credential. It can also write false audit rows attributed to any user (append-only does not prevent insertion). | The headline separation protects secret exfiltration, not misuse of the write credential. The real blast radius of an api compromise is "any member action in the project", the same as a worker compromise, minus offline reuse. Stating otherwise leads the architect to under-protect the api. | (1) Reword T7 and §5.1 to state the residual plainly. (2) The worker must re-validate approval *evidence* before each destructive step, not a flag: approver ≠ every requester (see SEC-R-2), approver held the role at approval time, step-up record exists and is recent, hash matches the recomputed plan, TC record matches target name + id. (3) Split the runtime DB role into `ovlm_api` and `ovlm_worker` with table/column grants: api has no SELECT on secret ciphertext columns and no write on run/step state; worker has no INSERT on approvals, sessions, users. (4) MVP, cheap off-DB copy: emit every audit row to the structured log stream at write time, so a DB-side rewrite is detectable against the log collector before the V1 hash chain exists. |
| SEC-R-2 | High | security-model §3.1, §3.2, §6.5, §7.1; T2, T9 | Separation of duties only checks "requester ≠ approver", where requester = plan creator / run starter. The person who chooses the code that runs as root on guests and as `ovlm-ansible` on the worker is the **profile version author** (automation ref + SHA, operator role), who is not in the requester set. Role bindings are per (user, role, scope) and nothing forbids one user holding `operator` and `approver` in the same scope. So user X edits the profile to SHA S, user Y creates the plan, X approves: X picked the code and approved it. Also, the approver is shown a SHA with no way to judge it. | T9's mitigation ("SHA bound into the approval hash") is only as strong as the review of that SHA. The two-person claim on retirement is unaffected, but the plan and cutover gates, which are where foreign code first runs, can be satisfied by one person. | (1) Define the requester set per gate as {author of the bound profile version, plan creator, run starter, anyone who edited the policy version in effect}; none may approve that gate. (2) Default policy: a user may not hold `operator` and `approver` in the same scope; if the admin allows it, it is audited and shown on every approval by that user. (3) The approval page and API response show every hash input (profile version, SHA, repo URL, target names + ids, data volume ids, policy version) and the diff of the automation repo between the last approved SHA for that service and the proposed one, or "first approval of this repo". (4) Add to §10 a test: profile author approving a plan built on that profile version is rejected. |
| SEC-R-3 | High | security-model §5.2, §6.4, §10 item 12; automation-contract §5, §7, §9 | §5.2 says secrets "never enter [logs, UI] by design; redaction only as backstop". Yet the design stores ansible-runner `job_events`, stdout and `--check --diff` output as run evidence and shows them in the run timeline. Module results and diffs contain whatever the playbook templates onto the guest, including **vault-decrypted workload secrets** (DB passwords, TLS keys, API tokens in app config), and gathered facts include `ansible_env` of the remote user. OVLM never knows these values in clear, so its exact-match redaction (contract §5) cannot remove them; the regexes catch only obvious shapes. The only control is `no_log: true` set by the playbook author, and the lint for it is "advisory" (contract §9). | Every renewal's `configure` run (and the reproducibility `--check --diff` against the live VM, contract §9) becomes a channel that copies workload secrets into the OVLM DB, backups and the UI of every `viewer`. This directly contradicts §5.2 and would fail the spirit of acceptance test 12 with a canary placed in a vault file. | (1) Reclassify automation artefacts as "may contain workload secrets": stored with restricted access (operator/admin in scope; viewers see result JSON and task status only), bounded retention separate from audit, excluded from any export. (2) `--diff` output is stored only when the profile opts in (`store_diffs: true`) with the risk stated; otherwise OVLM runs `--diff` but keeps only per-task changed/unchanged. (3) Make the `no_log` lint blocking for tasks whose module args reference vault variables or secret-like names, with a per-profile, audited waiver. (4) Tell playbook authors in the contract that OVLM stores task results. (5) Extend acceptance test 12: a canary inside an Ansible vault file never appears in stored artefacts. |
| SEC-R-4 | Medium | security-model §7.1 "approval binding"; functional-requirements FR-REG-2, FR-REN-6 | The approval binds (plan, profile version, automation SHA, target IDs, policy version). FR-REG-2 resolves the image "by name or property, **at renewal time**"; flavor and networks are also named, not pinned. The image actually booted on green is therefore not what the approver approved: anyone who can upload or replace an image visible to the project (project members, or the cloud operator for public images) changes the boot content after approval without voiding it. | The green VM's base content is the single largest input to what runs in production after cutover, and it is outside the approval hash. | Resolve image, flavor, network and port inputs to IDs at plan time and put them in the hash (image ID; its hash if Glance exposes one for the image — AS, not in OSI). | SEC-R-6 | Medium | security-model §7.1 preflight for "Detach production data volume" ("blue unlocked by owner, host up"); §4.2 | Two preflight conditions cannot be observed with the `member` credential. `host_status` is admin-only (OSI §1, SV), so "host up" is unknowable before the detach fails (`check_instance_host`, OSI §4, SV). `locked` and `locked_reason` are visible at mv 2.73 (OSI §1, SV) but whether the lock is an *owner* lock that the member can remove is not exposed in the server view (AS, not in OSI); an admin lock surfaces only as 403/409 at unlock (OSI §7, SV). | SEC-R-9 | Medium | security-model §3.2 last bullet, §7.1 (TC "Yes (at cutover approval)") | Policy may set a gate to "no approval" (plan, cutover). | SEC-R-10 | Medium | security-model §2.1 (TOTP is V1), §2.3 step-up, T1 | Step-up is "password within the last 5 minutes" per session, a bearer window: a hijacked session (XSS is mitigated, but malware, proxy logs, or a shared browser are not) can approve during any window the legitimate user opened. ## Claims checked against openstack-integration.md

All OpenStack permission statements in security-model §1.1, §1.2, T3, §4.1 (both tables), §4.2 (both tables), §4.3, §4.4, §6.1, §7.1 trace to an OSI section with the same tag. Three items are tagged AS by the author and are flagged above because a control depends on them: `os-getConsoleOutput` policy (SEC-R-19), SDK role list via `get_access()` (SEC-R-13), and cloud-init host-key regeneration (§6.2, acceptable as AS). One OSI recommendation (rec. 4, "blue's compute host up") is itself inconsistent with OSI §1 and is carried into the model (SEC-R-6).

## What is good and should stay

Worker-only write path with api unable to decrypt; envelope encryption with AAD binding ciphertext to its row; ownership guard that never trusts tags alone; approval hash that includes the automation SHA and policy version; human-only approvals with 403 for tokens; retirement two-person rule that cannot be relaxed; append-only audit via GRANTs plus trigger; GET-only client guard on the read session (once fixed per SEC-R-5); refusal to add `manager`; pinned SHA with branch refs rejected; guest output as untrusted data with external probe for cutover; the explicit list of operations a `member` cannot do, each ending in "stop, report, escalate". The acceptance criteria in §10 are concrete and testable; the required changes above add tests rather than replace them.
