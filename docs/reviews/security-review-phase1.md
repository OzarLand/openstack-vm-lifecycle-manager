## Verdict

**Accept with required changes.** The security model is coherent, honest about residual risk, and its OpenStack permission claims match openstack-integration.md in every case I checked (§1.1, §1.2, T3, §4.1, §4.2 both tables, §4.3, §4.4, §6.1, §7.1). The controls that matter most (two credentials, worker-only write path, ownership guard with DB-and-tag, approval hash binding, append-only audit at the GRANT level, pinned automation SHA, untrusted guest output) are the right ones. The gaps are mostly places where a stated guarantee is stronger than what the design delivers, or where a control is stated but its inputs are not observable with the credential OVLM holds.

## Architecture review (part 2)

Reviewed at commit `7a7ea43`: architecture.md, data-model.md, api-design.md, renewal-workflow.md, ADR-0002 to ADR-0006, and the updated functional-requirements.md. Focus: the renewal workflow's destructive steps, the credentials flow, and the two questions the architect asked. OpenStack tags as before; claims I could not trace to OSI are AS.

### Ruling (a): `renewal.auto_rollback_in_window` (default true)

**Accepted with conditions.** The in-window restore (S1–S9) mutates only resources whose IDs are in the approved plan hash and whose locks the run holds; the alternative is an open-ended outage while a human is paged. The named human owner of these actions is the G2 approver (or the operator who typed the cutover confirmation when policy needs no G2 approval): G2 covers "the whole downtime window" (ADR-0004), and the security model's rule that destructive actions need a named human owner is satisfied if, and only if, that approval explicitly includes the automatic restore. Conditions, tracked as SEC-R-30:

1. The G2 approval text, the `blast_radius` object and the audit row state "on failure inside the window OVLM automatically restores service to blue (stop green, move volume and FIP back, start blue)". The approver approves both directions.
2. The switch is a **policy** field (bound through the policy version in the plan hash), or at minimum its value is copied into the plan at creation and shown at G2. A global config key that an admin can flip after approval is not bound to anything the approver saw.
3. "Unambiguous state" is an enumerated table, not a judgement at implementation time: auto restore is allowed after failures of W2, W3 (volume rolled back to `in-use`, OSI §4 SV), W5 (not attached), W7, W8, W9 (nothing changed, OSI §6.1 SV) and W10; never after W1 or W6 (already `needs_human`), never when any of volume `status`, attachment list or FIP `port_id` could not be read, never while the OpenStack API is unreachable (renewal-workflow §5 already says so).
4. Exactly one automatic restore attempt per run; a restore failure is `needs_human`; the engine never re-enters the window automatically (the state machine already has no such edge; make it a tested invariant).
5. Audit: `principal_type=system`, `auth_method=none`, `action=restore.auto`, with the failing step, its error class and the G2 approval id as the authority reference.
6. Restore ignores policy windows (it is recovery), and it runs the quiesce on green (S2) before any detach; S2 failure stays `needs_human`.
7. Maintainer decision: after W7/W8 the data volume has been mounted read-write and a service has run on it. Automatic restore then starts blue on data a half-working green may have modified, with no snapshot unless the profile opted in. Either keep default `true` and state this in the policy help text, or default the W7/W8 case to `needs_human` unless `snapshot_before_handoff` is on. I recommend the second.

### Ruling (b): `claim_resources` exempt from guard rule 2

**Accepted, with the honest framing and conditions below (SEC-R-24).** For a pre-existing resource the marker proves nothing: OVLM sets it itself, so rule 2 ("target carries the OVLM tag") was never an authorization control for blue, the FIP or the volume. Its value there is visibility to other humans in the cloud and divergence detection after the fact. The authorization control for these targets is rule 1 (the ID is in the plan hash approved at G1), and B2 runs after G1 and after run start, so no write to a pre-existing resource happens without an approval. The exemption is therefore sound. Conditions:

1. State in ADR-0005 and security-model §4.3 that rule 2 adds no authorization for pre-existing resources; the DB plus G1 is the authority. Do not describe it as "the only exemption" from a security control it never was.
2. Marking must use **add/merge** semantics and never replace: Nova server metadata and Cinder volume metadata both have "replace all" and "merge" API forms (AS, not in OSI), and Nova tags have a per-tag add form (OSI §2 lists the policies, not the verbs). Using the replace form would wipe the workload owner's own metadata. Required: use the per-tag add and the merge form, read back after the call and verify every pre-existing key and tag is intact; lab test with a volume and a server carrying foreign metadata.
3. A server already at the 50-tag limit or 128 metadata items (OSI §2, SV) fails B2 `fatal` with a clear message, not `retryable`.
4. Marks stay after the run, so the orphan report must not list a FIP, volume or server that a current `service`/`managed_vm`/`profile_version` references (see SEC-R-25). Otherwise a completed renewal turns the production data volume into an "orphan".

### What is good in the architecture and should stay

Probe → decide → act → verify as the step contract; `WriteClient` constructible only in the worker inside a step context with a fencing token (extend it with SEC-R-7 and SEC-R-26); locks held by the run across retention; one convergent restore sequence; G2 before quiesce so the approval precedes the outage; no gate inside the window; data phases never interrupted; `OverQuota` fatal and `NoValidHost` bounded; admin-credential operations deliberately not built; no IDs or names in metric labels; per-project jump host with pinned key managed by admin, not by profiles; TOFU only as a profile change that forces re-approval.
