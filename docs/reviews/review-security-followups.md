## Verdict

**Fit to merge: not yet.** The five commits for SF-1, SF-3, SF-4, SF-5 and SF-10 (`401c891`, `d139c76`, `01b143b`,
`ec19998`, `8a769af`) are correct, strictly tighten what `main` had, and are fit to merge on their own. The lint-waiver

the whole repository (SFR-2). Both are small: one guard trigger plus one worker-side check, and one glob rule, each
with a test. Everything else below is low or informational and can follow.

(approver in scope, interactive session, TOTP-only step-up bound to the version, author and plan requesters refused,
operator+approver only with the installation setting, never a token, data-safety rules unwaivable by anyone, append-only
rows, waivers bound into the plan hash and applied by B6 exactly as bound) all hold at the API and were exercised

## Questions from the brief, answered

### SF-13, lint waivers

| Question | Answer |
|---|---|
| Can a waiver be granted without a human approver and a TOTP step-up? | Through the API: no. `authorize_action(LINT_WAIVER_GRANT)` is `approver` + `human_only` (`authz.py:105`), so a token is refused before anything else; `grant` then requires `is_human` and `auth_method == "password+totp"` on the session, consumes a step-up bound to `lint_waiver.grant` and the version id (user, session, action, target, unexpired, unused), and refuses one that was reached with a password alone (`waivers.py:152-193`; tested in `test_lint_waivers_api.py`, `renewal/test_lint_waivers.py`). Through the database as `ovlm_api`: **yes** (SFR-1). |
| Can the version's author, a plan requester or an API token grant one? | API: no. Author (`pv.created_by`), plan creators, approval requesters and run starters over every plan of the version (`plan_requesters`) are refused with `sod-violation`, whatever `allow_operator_approver` says; tokens are refused as above. Order gap: a granter who becomes a requester *later* is not caught (SFR-3). Database as `ovlm_api`: yes (SFR-1). |
| Can a waiver cover a data-safety rule? | No, by any role: `WAIVABLE_RULES` in the api and the `CHECK (rule IN (...))` in the table (`profiles_0002.py:35-36`); the probe as `ovlm_api` with `rule='formatting'` and a valid step-up failed on `lint_waiver_rule_check`. The unit test ties the two lists to the lint's own rule names. `no_log_secret`, `check_mode_forced`, `delegate_to`, `ignore_errors` are the only waivable rules; B6 applies a waiver only to `error` findings (`lint.py:408`). |
| Can a waiver be widened after a plan was approved without voiding the approval? | No. Rows are immutable except for a one-time revocation (trigger `lint_waiver_append_only`; `UPDATE … SET path_glob = '*'` as `ovlm_api` is refused, tested). Widening means a new row, and the plan hash binds `(id, rule, path_glob, granted_by)` of every **active** waiver (`plans.py:85-100`, recomputed by the worker from the live table in `load_facts`), so a grant or a revocation changes the hash and every approval bound to the old one fails check 1 (`evidence.py:195`). `test_a_new_waiver_changes_the_plan_hash` covers the grant; the revoke path is exercised in `test_b6_lints_with_the_waivers…`. A plan with no waivers keeps the hash it always had. |
| Can the `ovlm_api` role insert or alter waiver rows directly? Is the table append-only? | Insert: **yes, any row** that passes the CHECKs, in anyone's name, with any step-up (SFR-1). Alter: only the four revocation columns, once (column grants + trigger); `DELETE` and `TRUNCATE` are not granted and the trigger refuses `DELETE` for every role. The trigger function is owned by `ovlm_owner`; `ovlm_api` cannot drop, disable or replace it (no ownership, no `CREATE` on `public`, no `TEMP`). Append-only: yes. |
| Is the path glob safe? Can it match outside the repository or everything? Should a too-broad glob be refused? | Outside the repository: no, the linter derives every path relative to the checkout and raises on escape before matching (`lint.py:395-400`); the `/` and `..` checks are belt and braces. Everything: **yes**, `*`, `**`, `*/*`, `**/*` and `[a-z]*` are accepted (SFR-2). Yes, a glob without a literal component should be refused, and B6 should report how much a waiver matched. |

### SF-1 / CS-6, the worker container

| Question | Answer |
|---|---|
| Does any process keep uid 0 or `DAC_READ_SEARCH` after start-up? | No. The entrypoint (PID 1, root) copies the KEK through a `setpriv`-dropped `ovlm` child, then `exec`s `setpriv --reuid=10001 --regid=10001 --groups=10002 --inh-caps=+setuid,+setgid,+kill --ambient-caps=+setuid,+setgid,+kill --bounding-set=-all,+setuid,+setgid,+kill --no-new-privs -- /usr/bin/tini -- ovlm worker`. tini is PID 1 as `ovlm`; `DAC_READ_SEARCH` and `SETPCAP` are out of the bounding set, so no descendant can regain them. `init: true` is gone (docker-init would have stayed root with all five capabilities). The unit test ran the real script as root in this sandbox and checked `Uid 10001×4`, `CapPrm/Eff/Amb/Bnd == setuid|setgid|kill`, `NoNewPrivs 1`, `ARGS -- ovlm worker`. |
| Does `docker compose exec` without `-u` still give root with capabilities? | Yes: `user: "0:0"` with `cap_add [SETUID, SETGID, SETPCAP, KILL, DAC_READ_SEARCH]` is what `exec` inherits. Documented in compose.yaml and the install guide ("Shell access to the worker"); `make smoke` now uses `-u ovlm` for the new check and the entrypoint drop for the old one. Inherent to Docker; accepted (SFR-8a). |
| Is the KEK copy still safe? | Yes. Read once by root from `/run/secrets/worker_kek` (0400, host owner) as the stdin of a `setpriv`-dropped `ovlm` shell that writes `umask 077` into `/run/ovlm-kek` (tmpfs `mode=0700,uid=10001,gid=10001`, not traversable by `ovlm-ansible`), then atomic `mv`. The copy is never in an environment variable or argument; `OVLM_KEK__PRIVATE_KEY_FILE` names the copy. The healthcheck (`setpriv --reuid=10001 --regid=10001 --clear-groups --inh-caps=-all --bounding-set=-all --no-new-privs`) cannot read it either, having no capability and no supplementary group. `tini=0.19.*` is pinned to the bookworm series and `test -x` guards the build. |

### SF-3, SF-4, SF-5, SF-10 (regressions in the credential-store and host-key guarantees)

No TOTP, as the model records as accepted. `--reissue` audit: SFR-9.

## What was checked and found correct (SF-13 detail)

- **Grant path order**: 404 for a version out of the caller's `viewer` scope (no existence leak), 403 for non-approvers and tokens, 422 input shape, then the audited refusals (session, author, plan requesters, operator+approver), then step-up consumption **in the same transaction** as the insert, so a failed insert does not burn the step-up and a burnt step-up always has its row (`stepup_id` unique).
- **Revocation** only tightens: approver in scope, TOTP step-up bound to `lint_waiver.revoke` and the waiver id, `FOR UPDATE OF w`, 409 when already revoked, trigger refuses a second revocation.
- **B6** (`production.py:614-644`): the port loads the active waivers of the plan's profile version, hands them to `prepare_automation`, collects every `(finding, waiver)` the lint applied and writes one `automation.lint_waiver.applied` row per finding with run id, scope, rule, path, line, approver and reason, in its own transaction **after** the lint passed. `reverify_checkout` (restart, in-window) applies the same set without auditing again, which is right: B6 recorded the effect. `_LintingRunner` test runs the real lint on a real repository and checks the audit row and that a revocation makes the next B6 block again.
- **Hash**: `compute_plan_hash` adds `lint_waivers` only when non-empty; `create_plan`, `load_facts` (worker) and `request_approval` all use `hash_binding(active_waivers(...))`; `approval.hash_inputs` stores the list the approver was shown.
- **Imports**: `profiles.waivers` repeats the rule names rather than importing `automation` (import-linter contract kept; `make lint` green).
- **Smaller note, not a finding**: `_waivers()` and `_spec()` take the profile version id from `resolved` (api-written) while `load_facts` takes it from the `renewal_plan.profile_version_id` column. They agree whenever the api is honest, and `resolved` is itself bound by the hash the approver saw, so a mismatch cannot be introduced after approval. Reading the column in `_waivers()` would remove the question.
